# Windows-порт диктовалки: рекомендация по стеку

## 1. TLDR

Рекомендуемый стек — **Tauri v2 (Rust-бэкенд) с нативным треем**, без бандла WebView2 (используется системный рантайм), собранный в **NSIS**-инсталлятор (~15-25MB без модели) с **OV code-signing сертификатом** (не EV, не Azure Trusted Signing — гео-заблокирован для нашей юрисдикции) и **tauri-plugin-updater** на Ed25519/minisign — прямой структурный аналог связки Sparkle+EdDSA, которая уже используется на macOS. Глобальный хоткей (hold + toggle) — собственный `WH_KEYBOARD_LL`-хук на выделенном потоке со своим `GetMessageW`-насосом, а не `RegisterHotKey` (тот не даёт raw keyup и не умеет одиночные/модификатор-онли комбинации). Захват аудио — `cpal` с предварительно открытым и удерживаемым тёплым WASAPI-потоком (idle-close, не open-per-dictation), lock-free ring buffer между callback- и обработческим потоком. ASR — двойной путь как на macOS: облачный REST (как есть, плюс прогрев TLS-соединения в момент начала записи) и локальная ONNX-модель через `ort`, слинкованную ДИНАМИЧЕСКИ против официальной сборки Microsoft onnxruntime (не дефолтный prebuilt от pyke — тот падает на CPU до Haswell), CPU-only execution provider (GPU/DirectML — не в v1), плюс Silero VAD (16кГц/30мс) с preroll/hangover-буферами. Модель и аудио-девайс держатся тёплыми в памяти с idle-unload таймером. Вставка текста — clipboard + один батчевый `SendInput` (Ctrl-down/V-down/V-up/Ctrl-up), тегирование собственной инъекции через `dwExtraInfo`, отложенный generation-tracked возврат исходного clipboard; никакого TSF (у Open-Less свой TSF-компонент вешал explorer.exe) и никакого посимвольного pynput-стиля набора (у whisper-writer это главный источник Windows-багов). В v1 — только tray-иконка как индикатор записи (без отдельного HUD-окна, которое на Windows в Tauri крадёт фокус в отличие от macOS NSPanel — нерешённый на сегодня риск).

## 3. Выбор по подсистемам

### Оболочка/трей
**Рекомендация:** Tauri v2 (Rust) с нативным `tauri::tray::TrayIcon`, без бандла WebView2 (системный Evergreen-рантайм). **Обоснование:** проверено в коде — этот паттерн используют Handy (`src-tauri/src/tray.rs`), voicetypr (`src-tauri/src/menu/tray.rs`, 636 строк) и Open-Less (`lib.rs`, `TrayIconBuilder`); тех-ресёрч (gh release view) подтверждает реальные размеры 13-20MB для Tauri-based диктовалок против 7.3MB у чистого нативного Rust-трея (espanso) — разница в единицы мегабайт при заметной экономии на переиспользовании HTML/CSS для settings/history UI, которое у нас уже есть на macOS. **Альтернатива:** чистый native Win32 (Shell_NotifyIcon через `windows-rs`, без вебвью вообще) — минимальнее на пару MB и без WebView2-старта, но требует писать settings/history-UI на egui/winit с нуля; тех-ресёрч сам называет это «отдельная разработка, не изменение линии по умолчанию» — рассматривать как v2+-оптимизацию только если профилирование после MVP покажет, что WebView2-старт реально бьёт по latency хоткей→вставка.

### Глобальные хоткеи (hold + toggle)
**Рекомендация:** собственный `WH_KEYBOARD_LL`-хук на выделенном потоке со своим `GetMessageW`-насосом (не `RegisterHotKey`, не только `tauri-plugin-global-shortcut`). **Обоснование:** проверено в коде — voicetypr (`crates/keytrigger/src/backend/windows.rs`) и Open-Less (`hotkey.rs`, Windows-ветка строки 768-1105) реализуют именно так: хук+насос на одном потоке обязательны совместно, `AtomicBool`-латч против OS auto-repeat, own-injection tag в `dwExtraInfo` чтобы хук не триггерился на собственный синтетический paste, но пропускал сторонние инжекторы (AHK/Stream Deck). Open-Less использует эвристику длительности нажатия (`AUTO_HOLD_THRESHOLD = 350ms`) чтобы различать tap (toggle) и hold, плюс `HOTKEY_DEBOUNCE = 250ms` против случайного двойного нажатия — хорошие стартовые константы. Handy (`transcription_coordinator.rs`) добавляет ещё один слой — 30ms press-debounce + 50ms release-defer/cancel окно специально против auto-repeat-артефактов, с юнит-тестами на конкретный regression (issue #1539) — стоит скопировать концептуально. **Почему не `RegisterHotKey`/`tauri-plugin-global-shortcut`:** это утверждение из кода Handy — их собственный `handy-keys` крейт существует именно потому, что `tauri-plugin-global-shortcut` отклоняет одиночные клавиши (bare `fn`) и модификатор-онли комбинации; наш hold-режим может требовать именно такого. **Альтернатива:** `global-hotkey`/`tauri-plugin-global-shortcut` (как у Epicenter, vibe) — проще в реализации, даёт Pressed/Released через внутренний хук, приемлемо для v1, если hold-режим не требует одиночной клавиши/чистого модификатора; иначе сразу писать свой хук.

### Захват аудио
**Рекомендация:** `cpal`, двухпоточный паттерн — audio callback только даунмиксит в mono f32 и кладёт в lock-free SPSC ring buffer (без аллокаций/локов), отдельный воркер-поток делает resample (rubato) и финализацию. WASAPI-поток открывается заранее и держится тёплым (idle-close по таймауту), а не открывается заново на каждую диктовку. **Обоснование:** проверено в коде — Handy (`audio_toolkit`), vibe (`recorder.rs`, явно комментируют «zero-alloc в callback»), voicetypr (`Recorder.swift`-аналог, «与 Swift 版 Recorder.swift 行为对齐» — прямо заявляют выравнивание с нашим текущим Swift-стеком). Утверждение из блога/README (не код) — VoiceInk issue #572: даже с pre-warm пользователь замерил ~940мс задержки от хоткея до реального старта потока из-за renegotiation формата устройства на 192кГц/4ch девайсе; их воркэраунд — сторонний тул, держащий микрофон физически тёплым. Handy подтверждает в коде (managers/audio.rs) 40-110мс цену enumeration устройства без кэша — конкретное число, не оценка. **Альтернатива:** raw WASAPI напрямую через `windows-rs` без `cpal` — чуть меньше абстракции, но `cpal` чистый Rust без бандленных бинарников, а платформа всё равно только Windows — выигрыш минимален.

### Вставка текста (с учётом oʻ/gʻ)
**Рекомендация:** clipboard + ОДИН батчевый `SendInput`-вызов (Ctrl-down/V-down/V-up/Ctrl-up в одном вызове, не 4 отдельные инъекции), own-injection tag через `dwExtraInfo`, generation-tracked отложенный возврат исходного clipboard (500-750мс, срабатывает только если clipboard всё ещё содержит именно то, что мы туда положили). **Обоснование:** проверено в коде — voicetypr (`commands/text.rs::paste_windows`) объясняет прямо в комментарии, почему батч в одном вызове: 4 раздельные инъекции у rdev могут дать V раньше Ctrl (race регистрации модификатора); ретрай только при `sent == 0` (полный блок), без ретрая частичной отправки (чтобы не задвоить вставку). Про apostrophe-символы конкретно: clipboard передаёт произвольный Unicode как данные, без посимвольной трансляции через раскладку — это снимает риск для oʻ/gʻ по конструкции. **Fallback (не primary):** paced Unicode `SendInput` (`KEYEVENTF_UNICODE`, чанками — Open-Less использует `SENDINPUT_CHUNK_CHARS=16`/`SENDINPUT_CHUNK_DELAY=12ms`) — тоже безопасен для не-ASCII (кодирует `ch.encode_utf16`, корректно обрабатывает суррогатные пары — проверено в коде `unicode_keystroke.rs`), но здесь есть жёсткое предупреждение: НЕ пейсить нельзя — Open-Less зафиксировал в issue #491 реальный продовый инцидент, ~5-секундный фриз ВСЕГО десктопа (мышь, клавиатура, VSCode, браузер) от непейсированного `SendInput`, исправлено 4 PR-ами (#502/#503/#513/#514) именно введением пейсинга. **Явный анти-паттерн:** custom TSF text service — Open-Less его построил как основной путь и получил issue #665 (баг в TSF-DLL вешал explorer.exe целиком, потому что TSF грузится в каждый процесс системы) и незакрытый issue #852 (после TSF-вставки родная раскладка/IME пользователя не восстанавливается) спустя месяцы после релиза; учитывая приоритет минимализма, TSF строить не стоит вообще. Также анти-паттерн — посимвольная вставка без пейсинга/clipboard (whisper-writer/pynput, ломается об UIPI, issue #140). **Открытый риск, не решённый нигде из изученного:** даже проверенный в продакшене raw `SendInput` даёт silent fail в 5-10% случаев в некоторых приложениях (Epicenter/Whispering issue #841, признанно нерешено) — нужны верификация/ретрай и видимый fallback UX («скопировано в буфер, вставьте вручную»), а не предположение о 100%-надёжности.

### ASR (cloud-first vs локальная ONNX)
**Рекомендация:** сохранить оба пути, как сейчас на macOS, не делать v1 cloud-only. Локальная ONNX-модель — через `ort` (pykeio/ort), слинкованную ДИНАМИЧЕСКИ против официальной сборки Microsoft `onnxruntime` (SSE2-baseline + runtime MLAS dispatch), НЕ через дефолтную фичу `download-binaries` (prebuilt от pyke). **Обоснование:** проверено в коде — Handy (`Cargo.toml`, PR #1566) прямо документирует причину: pyke-prebuilt собран с жёстким `/arch:AVX2` baseline, исполняет BMI2/AVX-инструкции в статическом инициализаторе C++ и падает ДО `main()` на любом до-Haswell CPU или старом AMD — это был реальный продовый краш, а не гипотетический риск. CPU-only execution provider для v1, GPU/DirectML — не включать. Здесь важный нюанс без противоречия: DirectML реально даёт ускорение (проверено в коде, PR #985: 35.4с CPU vs 7.0с DirectML на 244с аудио, ~35x realtime) — Handy сам это измерил и всё равно откатил (PR #1566) из соображений надёжности на старом железе, а не потому что GPU медленнее. Для нашего кейса (секунды аудио на диктовку, не 244-секундные файлы) выигрыш GPU практически не виден на латентности одной фразы, а цена — целый класс проблем: OOM на загрузке модели, «мусорный» вывод на AMD GPU, и у Handy — утечка Vulkan-контекста на гибридных GPU-ноутбуках, деградирующая производительность системного композитора ДО конца жизни процесса (issue #1775) — весомый аргумент остаться CPU-only в v1. VAD — Silero ONNX на 16кГц/30мс-кадрах (480 сэмплов), с preroll-буфером ~150-250мс до подтверждения речи и hangover-хвостом ~150-250мс после — параметры эмпирические, тюнить под uz/ru/en отдельно (утверждение из блога/README о конкретных цифрах RealtimeSTT: `pre_recording_buffer_duration`/`post_speech_silence_duration` дефолт 0.2с — стартовая точка, не финальное значение). Модель и её загрузка держатся тёплыми в памяти с idle-unload — это единственный паттерн, который абсолютно единогласно повторяется во ВСЕХ изученных проектах без исключения (Handy `TranscriptionManager`, Epicenter `ModelCache`, VoiceInk `WhisperModelWarmupCoordinator`, voicetypr `CachedContext`, Open-Less `SherpaOnnxRuntime`, RealtimeSTT `TranscriptionWorker`, whisper-writer `local_model`) — не переизобретать, копировать без сомнений. Прогрев модели тестовым аудио при старте приложения (и по возможности при wake) — тот же консенсус (VoiceInk `ModelPrewarmService`, RealtimeSTT `warmup_audio.wav`, Epicenter `prewarm_model` на VAD-arm). Для облачного плеча — прогрев TLS/TCP-соединения (HEAD-запрос в момент СТАРТА записи, а не после её конца) — проверено в коде voicetypr (`CloudProvider::warm_up()`), дешёвая мера, прямо режущая хвостовую задержку. **Пропустить в v1:** streaming/incremental partial-decode ASR — реальная сложность (UI для committed/tentative текста, отмена, стабилизатор типа `WordAgreementEngine` у VoiceInk) ради выигрыша меньшего, чем то, что уже даёт тюнинг VAD-хвоста + тёплая модель + прогрев; пересмотреть в v2, только если после запуска латентность «конец речи → вставленный текст» останется топ-жалобой пользователей.

### Оверлей-HUD
**Рекомендация для v1:** обойтись без отдельного HUD-окна, индикация записи — только сменой tray-иконки (Idle/Recording/Transcribing), как параллельный слой у Handy. **Обоснование:** проверено в коде — на Windows/Linux обычное Tauri `WebviewWindow` КРАДЁТ фокус по клику в отличие от macOS, где Epicenter специально оборачивает overlay в non-activating `NSPanel` через `tauri-nspanel`; для Windows такого решения ни в одном изученном проекте нет — это подтверждённый в коде и оставленный открытым риск, а не решённая проблема. Если HUD всё же понадобится (v2): маленькое always-on-top окно фиксированного размера, переиспользуемое между состояниями, а не пересоздаваемое — паттерн Handy (`overlay.rs`, 256x46 pill) и vibe (`dictation_indicator.rs`, 280x64, `skip_taskbar`, `ignore_cursor_events` для click-through). **Альтернатива при реальной необходимости не красть фокус:** нативное layered Win32-окно (`WS_EX_NOACTIVATE`/`WS_EX_LAYERED`) вместо Tauri `WebviewWindow` — ни один изученный проект это не реализовал на Windows, придётся строить с нуля.

### Автообновление
**Рекомендация:** `tauri-plugin-updater` с Ed25519/minisign-подписью (`tauri signer generate`, приватный ключ в CI, публичный в `tauri.conf.json`). **Обоснование:** утверждение из тех-ресёрча (документация Tauri v2 + анализ реальных релизов через gh CLI) — это прямой структурный аналог macOS-связки Sparkle+EdDSA: свой JSON-фид на своём сервере, тихая фоновая загрузка и установка NSIS-бандла; используется как есть в Handy, vibe, voicetypr, Open-Less (проверено в коде каждого). **Явно НЕ Velopack:** даёт бинарные дельта-патчи и Authenticode-подпись вместо отдельной криптосхемы, но добавляет чужеродный C#/NuGet-подобный шаг поверх Rust/Tauri-пайплайна ради экономии, малозначимой при инсталляторе 13-20MB (вывод тех-ресёрча) — пересмотреть только если бинарь разрастётся или апдейты станут очень частыми при большой базе.

### Инсталлер + подпись
**Рекомендация — инсталлер:** NSIS, дефолтный бандлер Tauri v2. **Обоснование:** проверено на реальных релизах (gh release view) — NSIS вдвое компактнее WiX/MSI на идентичных данных (Handy: NSIS x64 20.9MB vs MSI 44.7MB). MSI/MSIX — пропускаем, не нужен enterprise-деплой; собственный MSI-путь Open-Less требовал ручного `light.exe`-релинка из-за `ICE80`-ошибок при смешивании x86/x64 IME-DLL под одним WiX Directory — лишняя поддержка ради того, чего у нас нет. **Критически — не бандлить ffmpeg/полные рантайм-инсталляторы без необходимости:** проверено в коде — vibe (45.3MB) и особенно voicetypr (325.8MB, в 4-5 раз тяжелее macOS-сборки того же проекта) раздувают инсталлятор именно бандлом ffmpeg+vc_redist+VulkanRT внутри NSIS-пейлоада; если наш локальный ONNX/whisper.cpp-путь всё же тянет VC++ Runtime (подтверждено в коде voicetypr — `whisper-rs` на Windows требует `vcomp140.dll` даже при `+crt-static`), использовать условный NSIS-хук (проверка registry-ключа, silent-install `/passive /norestart` только если отсутствует), а не постоянный бандл.

**Рекомендация — подпись:** классический OV-сертификат (SSL.com/Sectigo/Certum, ~$130-250/год). **Обоснование:** утверждение из блога/документации (не код) — тех-ресёрч через Microsoft-документацию и блог ToDesktop показывает, что Azure Trusted Signing геозаблокирован (только США/Канада/ЕС/UK, с 2026 ещё и 3+ года истории юрлица) — не подходит нашей юрисдикции; EV с 29 февраля 2024 больше не даёт мгновенного бонуса SmartScreen-репутации (официальная политика Microsoft), только лишний HSM/токен и цена. Держать ОДИН стабильный Publisher/сертификат из релиза в релиз — репутация копится по объёму чистых загрузок, не по типу сертификата (это тоже утверждение из документации Microsoft, а не измерение). **Почему подпись — не опция, а обязательный пункт v1:** проверено в коде/issue-трекерах — КАЖДЫЙ проект, шипнувший Windows-сборку без Authenticode-подписи (только с updater-подписью minisign или вовсе без подписи), получил повторяющиеся AV false-positive инциденты: voicetypr issue #37 (Kaspersky удаляет файлы и форсит перезагрузку машины пользователя), vibe issues #1/#71/#126/#166/#294/#335/#377/#725 (2024-2026, Wacatac.B!ml/H!ml, Bkav AIDetectMalware), Whispering issues #440/#273/#73 (Trojan-детекты, включая сам деинсталлятор). Это не гипотетический риск, а зафиксированный повторяющийся паттерн.

## 4. Скоуп v1 и v2

**v1 (минимальный жизнеспособный порт):**
- Tray-shell на Tauri v2 + Rust, HTML/CSS для настроек/истории (без отдельного полноценного окна сверх необходимого)
- Собственный `WH_KEYBOARD_LL`-хук, hold + toggle, debounce/interruption-window state machine
- `cpal`-захват, тёплый WASAPI-поток с idle-close, lock-free ring buffer
- Silero VAD (ONNX) + локальная ASR-модель (та же, что на macOS, через `ort` динамически против официального MS onnxruntime, CPU EP)
- Облачный REST ASR — как есть, плюс TLS-прогрев на старте записи
- Вставка текста: clipboard + батчевый `SendInput` Ctrl+V, own-injection tag, generation-tracked восстановление clipboard
- Индикация записи — только смена tray-иконки (без HUD-окна)
- История диктовок (тот же формат данных, что на macOS)
- `tauri-plugin-updater` (minisign) + NSIS + OV-подпись
- Явно НЕ входит: GPU/DirectML EP, streaming/partial ASR, TSF, Microsoft Store канал, ARM64-сборка

**v2 (по факту реальных пользовательских жалоб после запуска):**
- HUD-окно поверх других, если tray-иконки окажется недостаточно как обратной связи; решить вопрос кражи фокуса (нативное layered-окно, если Tauri `WebviewWindow` не устроит)
- Paced Unicode `SendInput` как явный fallback-переключатель для приложений, где clipboard-paste не проходит (elevated-окна, RDP/сэндбокс) + видимое уведомление «скопировано, вставьте вручную»
- Опциональный DirectML/GPU EP с явным CPU-фолбэком — только если профилирование на реальном железе покажет, что CPU — узкое место
- Streaming/incremental ASR с частичным текстом — если латентность «конец речи → вставка» останется топ-жалобой
- ARM64-сборка (Snapdragon X), если появится такая аудитория
- При необходимости — донастройка/замена модели под качество uz/ru/en, если возникнут явные проблемы с качеством распознавания

## 5. Риски и открытые вопросы

- **Качество ASR на узбекском:** ни один изученный каталог локальных моделей (sherpa-onnx у Open-Less, faster-whisper, whisper.cpp GGUF) не валидирован конкретно на узбекском — риск на уровне выбора модели, не архитектуры; нужно отдельно подтвердить, что наша текущая macOS-модель даёт то же качество через `ort` на Windows CPU.
- **Надёжность вставки текста:** даже у самого Windows-QA-зрелого проекта из изученных (Epicenter/Whispering) — НЕРЕШЁННЫЙ silent-fail paste в 5-10% случаев на raw `SendInput` (issue #841, признано открытым). Нужны верификация/ретрай и видимый fallback, а не предположение о гарантированной доставке.
- **Elevated/UIPI foreground-окна:** хоткей/вставка может зависнуть или молча не сработать, если целевое приложение запущено с повышенными правами, а наше — нет (Handy issue #434, обходной путь maintainer'а — «тоже запускать от админа», нам не подходит по умолчанию). Нужна явная детекция и деградация, ни у кого из изученных чистого решения нет.
- **Кража фокуса HUD-окном на Windows:** ни один проект не решил «always-on-top HUD, никогда не крадущий фокус» на Windows (на macOS решение бесплатное через NSPanel). Открытый вопрос архитектуры, если HUD войдёт в v2.
- **AVX2-baseline-краш:** обязательно протестировать выбранную схему линковки onnxruntime на реальной до-Haswell/старой-AMD машине перед релизом — не полагаться на предположение «современный CPU есть у всех» (Handy это уже ловил в проде).
- **Время на подпись и репутацию:** выпуск OV-сертификата плюс накопление SmartScreen-репутации (постепенное, без быстрого пути с февраля 2024) требует реального календарного времени — начинать эту ветку рано, не оставлять на неделю релиза.
- **VC++ Runtime-зависимость:** любой whisper.cpp/OpenMP-линкованный Rust-крейт тянет `vcomp140.dll` независимо от `+crt-static` (подтверждено в коде voicetypr) — решить явно (условный NSIS-хук установки vc_redist), не обнаруживать на чистой машине пользователя постфактум.
- **Гибридные GPU-ноутбуки:** если GPU EP всё же появится в v2 — задокументированный инцидент Handy показывает, что инициализация Vulkan-контекста против нескольких GPU может деградировать производительность системного композитора на весь срок жизни процесса — сильный аргумент за строго CPU-only, даже при явном соблазне ускорения.
- **Tauri vs чистый native:** оценка тех-ресёрча — чистый Rust без вебвью экономит единицы мегабайт против Tauri (13-20MB) ценой реальной разработки settings/history UI с нуля; рассматривать только как v2+-оптимизацию при подтверждённой проблеме с latency хоткей→вставка, не как решение по умолчанию.

## 6. Грубая оценка объёма работ по подсистемам

*Оценки — солодев/малая команда, знакомая с текущим macOS-кодом (не с нуля), в рабочих днях.*

| Подсистема | Оценка |
|---|---|
| Shell/tray + Tauri-скаффолд + settings/history UI (HTML/CSS/TS) | 5-8 дней |
| Глобальный хоткей (WH_KEYBOARD_LL, hold/toggle state machine, debounce) | 4-6 дней |
| Захват аудио (cpal, тёплый WASAPI, ring buffer, resample) | 3-5 дней |
| Вставка текста (clipboard+SendInput батч, инъекция-тег, restore) + edge cases (elevated-окна, ретрай) | 5-8 дней (наибольший риск-сёрфейс) |
| Локальная ASR-интеграция (ort + динамический линк onnxruntime, warm/idle-unload, тюнинг VAD) | 6-10 дней |
| Облачный REST ASR-путь | 1-2 дня (в основном переиспользование текущего клиента/протокола) |
| Индикация записи (tray-иконка в v1; HUD — если войдёт в scope) | <1 день (tray-only) / 2-4 дня (HUD) |
| Инсталлер (NSIS) + настройка подписи + апдейтер | 4-6 дней (без учёта времени на получение сертификата) |
| QA-проход по известным Windows pitfalls (elevated-окна, sleep/wake, non-AVX2 CPU, AV false-positive проверка) | 3-5 дней |
| **Итого v1** | **≈35-55 рабочих дней**, плюс параллельный (не блокирующий) лид-тайм на получение OV-сертификата и накопление SmartScreen-репутации |
